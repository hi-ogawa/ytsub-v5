# User Authentication System

Prerequisite for extension ↔ server sync (see `2026-03-10-extension-server-integration.md`).

## Problem

Current auth is a single hardcoded password hash — no user accounts, no `userId` scoping. All data is implicitly owned by one user. To support the extension as a server client (and eventually multi-user), we need a real user system.

## Current state

- **Auth gate:** `src/server/auth.ts` — password verified against `AUTH_PASSWORD_HASH` env var, HMAC-signed session cookie via `@orpc/server/helpers` `sign`/`unsign`
- **Auth routes:** `src/server/routes/auth.ts` — REST login/logout/check (not oRPC, needs `Set-Cookie` headers)
- **Middleware:** `pub` (public) and `authed` (requires valid session) base procedures in `src/server/auth.ts`
- **Schema:** no `users` table, no `userId` on videos/bookmarks/captions
- **Login UI:** `src/components/login.tsx` exists but not wired into app routing
- **Env vars:** `AUTH_PASSWORD_HASH` (SHA-256 hex), `AUTH_SECRET` (HMAC signing key)

## Scope

Standard username/password auth with per-user data isolation.

### Schema changes

- **New `users` table:** `id`, `email`, `passwordHash`, `createdAt`
- **Add `userId` column** to `videos` table (FK → users, cascade delete)
- `captions` and `bookmarks` already cascade from `videos`, so no direct `userId` needed
- **Migration:** add column (existing data can start from scratch, no backfill needed)

### Auth endpoints (evolve existing)

- **Register:** `POST /auth/register` — email + password + Turnstile captcha token → create user, return session
- **Login:** `POST /auth/login` — email + password → verify, return session cookie
- **Logout:** `POST /auth/logout` — clear cookie
- **Check:** `GET /auth/check` — return authenticated user info
- Session token: HMAC cookie with `userId` + `exp`, auto-refresh on requests

### Middleware changes

- `authed` middleware extracts `userId` from session token, adds to context
- All queries scoped by `context.userId`

### Web app integration

- Wire login component into app routing (redirect on 401)
- Registration page (or combined login/register form)

### Extension auth

- Server URL is hardcoded (build-time constant — currently `ytsub-v5.hiro18181.workers.dev`, will change after rename to `zamak`)
- Login flow in extension popup or settings page (email/password)
- Store session token in `chrome.storage.local`
- Background worker attaches token to API requests

## Decisions (resolved)

1. **Registration flow** — open signup/login with Cloudflare Turnstile captcha. Simple.
2. **Token format** — session cookie with auto-refresh. Same for web app and extension.
3. **Migration** — start from scratch. No need to backfill existing data.

## Implementation steps

1. Schema: add `users` table, add `userId` to `videos`, create migration
2. Auth helpers: update `signToken`/`verifyToken` to include `userId`
3. Auth routes: add register, update login to query `users` table
4. Middleware: extract `userId` from token, inject into context
5. Query scoping: update all video/bookmark queries to filter by `userId`
6. Web app: wire login/register UI into routing
7. Extension: login flow in popup/settings (email/password, reuses session cookie)

Note: worker rename (`ytsub-v5` → `zamak`) should happen first — see PRD backlog.
