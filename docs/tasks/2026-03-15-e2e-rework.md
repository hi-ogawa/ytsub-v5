### Where time goes

- **Sync tests** (6 tests across dev-viewer + video-list): ~20s = 24% of suite. Each creates bookmarks → pushes → clears → pulls — multi-step flows with page reloads.
- **dev-viewer panel tests** (23 non-sync tests): ~16s. Each pays login + navigate + openPanel cost.
- **API tests** (21 tests in api + auth): <1s total — negligible.

## Issues

### 1. Duplicated helpers (~100 lines repeated 3x)

`openPanelWithTracks()` and `createBookmarkAt()` are copy-pasted identically in:

- `dev-viewer.spec.ts` (lines 5-37)
- `video-list.spec.ts` (lines 57-88)
- `ai-prompt.spec.ts` (lines 4-35)

### 2. Too many small tests that could be merged

Several tests are thin wrappers testing one tiny assertion that could be combined into a richer flow test without losing signal. Examples:

- **dev-viewer.spec.ts**: "tab bar shows captions and bookmarks tabs" (1 assertion), "bookmarks tab shows empty state" (1 assertion), "bookmark count shown in tab label" (1 assertion) — these three test the same tab bar and could be one test walking through states
- **dev-viewer.spec.ts**: "cancel text selection hides FAB" (2 assertions) — could fold into "manual bookmark: create, highlight, and export"
- **dev-viewer.spec.ts**: "captions tab preserves scroll after switching tabs" — just checks `[data-index='0']` is visible after tab switch, barely tests anything
- **basic.spec.ts** + **auth.spec.ts** overlap: both test login/register/duplicate-username/wrong-password, one via UI and one via API. The UI tests in basic.spec.ts duplicate what the login helper already exercises every test run

### 3. `workers: 1` — no parallelization

The main bottleneck. Each file's `beforeAll` calls `setupDb()` which clears + reseeds the DB, so files can't run in parallel because they share one DB state.

**Fix options:**

- (a) Per-worker DB isolation (e.g., separate D1 databases per worker)
- (b) Group tests by DB setup needs — files with `setupDb()` (no seed) can share a worker, files with `setupDb({ seed: true })` share another
- (c) Use `test.describe.configure({ mode: 'parallel' })` within files where tests are independent (most are, since each `beforeEach` does a fresh login + navigate)

### 4. Each test pays login cost

Every `beforeEach` runs through the full login UI flow (goto /login → fill → click → wait). With 80 tests, that's 80 login flows. Playwright supports `storageState` to reuse auth — login once in global setup, save cookies/localStorage, reuse in all tests.

### 5. `rpc()` helper duplicated between auth.spec.ts and api.spec.ts

Different implementations with the same signature.

## Proposed Changes

### Phase 1: Quick wins (no behavior change)

1. **Extract shared helpers to `e2e/helper.ts`**
   - Move `openPanelWithTracks()`, `createBookmarkAt()` to helper
   - Add `FIXTURE_VIDEO_ID` constant
   - Remove 3 copies from test files

2. **Merge thin tests in dev-viewer.spec.ts**
   Combine related micro-tests into richer flow tests:
   - Merge tab bar / empty state / bookmark count → "bookmarks tab lifecycle"
   - Merge cancel selection + scroll preservation into existing tests
   - Target: ~29 → ~20 tests

3. **Consolidate auth tests**
   - basic.spec.ts has 6 auth UI tests + auth.spec.ts has 11 API auth tests = 17 auth tests
   - Merge basic.spec.ts auth tests into auth.spec.ts (one "auth" file)
   - Keep only the nav/routing tests from basic.spec.ts that aren't auth-specific

4. **Merge small single-purpose files**
   - `theme.spec.ts` (1 test) + `toast.spec.ts` (2 tests) → fold into a `ui.spec.ts` or into existing files
   - `delete.spec.ts` (2 tests) → could merge into `video-list.spec.ts` (delete video) and `dev-viewer.spec.ts` (delete bookmark)

### Phase 2: Speed improvements

5. **Persistent auth via `storageState`**
   - Login once in `global-setup.ts`, save to `e2e/.auth/user.json`
   - Reference in playwright config: `use: { storageState: 'e2e/.auth/user.json' }`
   - Remove `login(page)` from every `beforeEach`
   - Login is fast (~0.3s) but it adds up across 55+ browser tests

6. **Enable parallel workers**
   - Most tests don't need seed data or use independent fixture data
   - Group tests by DB isolation needs:
     - **No-DB tests** (dev-viewer, theme, toast): use fixture data only — fully parallelizable
     - **Fresh-DB tests** (api, auth): create own data — parallelizable if separate DB
     - **Seed-DB tests** (video-list sync, dev-viewer sync, delete, import): need seed — run serially or with isolated DB
   - Start with `workers: 2` or `fullyParallel: true` for the no-DB group

7. **Reduce `beforeAll(setupDb())` calls**
   - Move DB setup to `global-setup.ts` (runs once for entire suite)
   - Tests that need clean state can clear specific records rather than full DB wipe

### Phase 3: Optional cleanup

8. **Inline `beforeEach` navigation patterns**
   - Many tests do `login(page)` → `page.goto(...)` → `openPanelWithTracks(page)` — could be a single `setupViewer(page)` helper

9. **Extract API test helper**
   - Unify `rpc()` and `getAuthCookie()` into `e2e/api-helper.ts`
